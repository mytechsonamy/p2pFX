# Database portability: Postgres and Oracle

Status: plan, draft 1 (2026-10-15). Scope: what it takes to run the API on Oracle 19c+ as well as Postgres 16. No code
has changed yet.

Recommendation: keep hand-written SQL, put it behind a repository boundary with a thin dialect layer, and keep two
migration folders (`db/migrations/postgres`, `db/migrations/oracle`). Do not adopt an ORM. The code depends on exact
money columns, explicit row locks, conditional updates and idempotent inserts, and an ORM would hide exactly those.
Replace the three Postgres-only mechanisms (LISTEN/NOTIFY, advisory locks, transactional DDL) with portable designs
first, on Postgres, while the test suite stays green. Only then add the Oracle implementation and run CI against both
databases. Rough total: 18 to 27 developer-weeks (estimate).

README and architecture doc name LISTEN/NOTIFY and an advisory lock as part of the design.

How the database is reached today:

- `apps/api/src/db/pool.ts` creates a `pg.Pool`, parses `int8` as `BigInt` (line 4) and leaves `numeric` as strings.
  Prices therefore arrive as decimal strings and quantities as `bigint`. Parameters are passed as `bigint`, and `pg`
  sends them as text. Nothing passes through a JS `number`.
- `tx(db, fn)` (pool.ts:74) runs `begin`/`commit` on one client. It is used in 8 places. Other code calls
  `db.connect()` directly to hold a session lock on a dedicated connection (exchange.ts:152, settlement.ts:86,
  config-service.ts:39, migrate.ts:10).
- `Db` (the pool) is passed by constructor to every service, and `Queryable` (pool or client) to helpers such as
  `appendEvent`, `audit` and `loadOrder`. There is no repository layer: services and routes write SQL inline.
- `migrate.ts` applies each file in one transaction under `pg_advisory_lock(727274)`. This relies on transactional DDL.
- `events.ts` publishes every stream event (book, trade, order, fill, LP tick) with `pg_notify`; each instance has one
  `Listener` connection (pool.ts:20) that reconnects with backoff. Delivery is best effort by design.
- `config-service.ts` uses a second channel, `p2p_config`, to tell other instances to reload configuration.
- Matching leadership (exchange.ts:151-219, migration 007): `pg_try_advisory_lock` on a dedicated connection, then the
  leader bumps `matching_leader.epoch`. Every matching write runs `select epoch ... for share` in its own transaction
  (`fence`, exchange.ts:203), so a former leader cannot commit after a takeover.
- Tests (`apps/api/test/helpers.ts`) drop and recreate the `public` schema before each harness, then let `buildApp`
  migrate. Test files run one at a time (`vitest.config.ts`). CI runs one `postgres:16` service.

## 3. Target design options

| | (a) Raw SQL, thin dialect layer, two migration sets | (b) Query builder (Kysely) | (c) ORM (Prisma, TypeORM, MikroORM) |
|---|---|---|---|
| Oracle support | node-oracledb, Oracle's own driver. Thin mode (no Instant Client) supports DB 12.1+, binds `BigInt` since 6.5 | Not in Kysely core (Postgres, MySQL, SQLite, MSSQL). Community dialects exist; MikroORM 7 ships one inside `@mikro-orm/sql`. Maturity not proven by us | Prisma: no Oracle. TypeORM: Oracle driver for years, uneven quality. MikroORM: `@mikro-orm/oracledb` new in v7 (2026); we have no experience with it |
| What we write per dialect | The ~20 statements that differ in kind (upserts, `RETURNING`, locks, reports) | Fewer, but upserts, `RETURNING`, locks and JSON still need dialect branches | Migrations, plus raw SQL for locking and reports anyway |
| Money values (`bigint`, `NUMBER(24,8)`) | Full control: fetch as string, convert in the row mapper | Driver-level type handlers still needed; builder types do not enforce them | Each ORM maps `bigint` and `decimal` differently; extra care to keep strings |
| Row locks, conditional updates, idempotent inserts | Written out, reviewed as SQL | Supported, but readable only by knowing the builder | Conditional `update ... where status = ...` with row count, `FOR UPDATE SKIP LOCKED`, `ON CONFLICT` usually drop to raw SQL |
| Migrations | Two hand-written folders | Same as (a): Kysely migrations are code, but DDL still differs | Generated per dialect from a model; review of generated Oracle DDL needed |
| Churn in existing code | Medium: SQL moves into repositories, mostly unchanged | High: every statement rewritten | Highest: data access rewritten around entities |
| Fit for bank DBA review | Plain SQL files the DBA can read | Generated SQL, visible only in logs | Generated SQL |

Recommendation: (a). The reasons, in order:

1. The risk is in a small number of statements whose exact semantics matter: the fill transaction
   (exchange.ts:709-770), idempotent order entry (order-entry.ts:142), the bank quote claim (dealing.ts:145-170) and
   the settlement state machine (settlement.ts). We want those written by hand for each database and reviewed as SQL,
   not generated.
2. Most of the other ~140 statements are plain CRUD. A small dialect object (placeholders, `limit`, `IN` expansion,
   booleans, `RETURNING`) handles them without a builder.
3. Oracle support in the TypeScript builders and ORMs is either missing (Prisma) or young (Kysely community dialects,
   MikroORM 7). We are not confident enough in any of them to put settlement on it. This could change; revisit in a
   year.
4. Banks' DBAs review schema and SQL. Plain files make that review possible.

If the team prefers a builder for the CRUD statements later, (a) does not block it: repositories can use Kysely inside
for Postgres and keep hand-written Oracle SQL.

## 4. The hard parts

### 4.1 Driver behaviour and the `Db` boundary

Replace `Db = pg.Pool` with an interface the API owns:

```ts
interface Db {
  dialect: 'postgres' | 'oracle';
  query<T>(sql: Sql, params?: unknown[]): Promise<T[]>;
  execute(sql: Sql, params?: unknown[]): Promise<{ rowCount: number; returning?: Record<string, unknown> }>;
  tx<T>(fn: (t: Tx) => Promise<T>): Promise<T>;
}
```

Services stop writing SQL. Each aggregate gets a repository (`OrderRepo`, `FillRepo`, `SettlementRepo`, `DealRepo`,
`HedgeRepo`, `ConfigRepo`, `EventStore`, `OpsUserRepo`, `ReportsRepo`) with a Postgres and an Oracle implementation
that share the plain statements and differ where section 2 says. Row mappers return the same TypeScript types
(`OrderRow` and friends) on both, so the engine, settlement and routes do not change.

Driver settings that must be set once, in the Oracle `Db`:

- Fetch every `NUMBER` as a string (`fetchTypeHandler`) and convert in the mapper: `bigint` columns to `BigInt`, price
  columns stay strings. The default (JS `number`) silently loses precision above 2^53 and on 8-decimal prices.
- Bind `bigint` values directly (supported since node-oracledb 6.5). Never convert to `number`.
- Fetch `CLOB` as string and parse JSON columns in the mapper.
- `autoCommit` is off by default in node-oracledb. Statements outside `tx()` must commit, or they hold locks until the
  connection is reused.
- Set the session time zone to UTC on every new connection, and bind `Date` values as `TIMESTAMP WITH TIME ZONE`.
- Use Thin mode, so the container does not need Oracle Instant Client.

Transaction semantics differ in one useful way: a failed statement in Oracle rolls back only that statement. Code that
catches `ORA-00001` inside a transaction can continue. In Postgres the same pattern needs a savepoint.

### 4.2 Matching leadership without advisory locks

Today the lock is held by a connection, and losing the connection loses leadership at once. Oracle has `DBMS_LOCK`
with the same session semantics, but it needs an `EXECUTE` grant that bank DBAs often refuse. We should not depend
on it.

Proposed design, the same on both databases:

- `matching_leader` gets `lease_until` and `holder`. Starting instances try
  `UPDATE matching_leader SET epoch = epoch + 1, holder = :me, lease_until = :now + :ttl WHERE id = 1 AND (lease_until < :now OR holder = :me)`.
  One row updated means leadership. The leader renews every `ttl / 3` (for example 5 s renewal, 15 s TTL) and stops
  matching if a renewal fails or is late.
- Fencing stays. Oracle has no `FOR SHARE`, and locking the single row `FOR UPDATE` would serialise all pair workers.
  Instead add `matching_fence (pair, epoch)` with one row per pair. Each matching write locks its own pair's row
  (`SELECT epoch FROM matching_fence WHERE pair = :p FOR UPDATE`) and compares the epoch. A takeover updates every row
  to the new epoch, so it waits for in-flight writes, exactly as today. Pair workers do not block each other.
- Cost: failover takes up to the TTL instead of being immediate on connection loss. A paused leader (GC, VM freeze)
  is still safe because of the fence.

This replaces exchange.ts:151-219 and the takeover test in `v11-general-review.test.ts:193`.

### 4.4 Event bus and config reload without LISTEN/NOTIFY

Two channels, different needs:

- `p2p_config`: rare, must not be missed. Poll `SELECT MAX(version) FROM config` every 2 s and reload when it moves.
  This is also how a reconnect is handled today. Simple, no grants.
- `p2p_events`: frequent (every LP tick, book change, fill), best effort, consumed by WebSocket clients on every
  instance. Behind an interface `StreamTransport { publish(e); subscribe(fn) }` with three implementations:
  1. `PgNotifyTransport`: today's code.
  2. `LocalTransport`: in-process `EventEmitter`. Correct when one instance serves all WebSockets, which is the
     expected size for one bank's retail volume.
  3. `OutboxPollTransport`: `INSERT` into `stream_outbox (id identity, payload, created_at)`; each instance polls
     `WHERE id > :last ORDER BY id FETCH FIRST 500 ROWS ONLY` every 200 ms; the scheduler deletes rows older than a
     minute. LP ticks are coalesced per pair before insert.

  Oracle AQ (Transactional Event Queues) would give push delivery, and node-oracledb supports AQ in Thin mode since
  6.10. It needs queue creation grants and DBA involvement, so treat it as an option per bank, not the default.
  `DBMS_ALERT` is not suitable: signals are serialised at commit and the payload is small. Continuous Query
  Notification needs the database to reach the client, which bank networks usually block.

The durable `events` table (event-store.ts) is not affected: it is already a plain table written in the caller's
transaction. Only the pair sequence upsert (event-store.ts:43) and the version subquery need dialect versions.

### 4.5 Migrations

Two folders, hand-written, one ledger each:

- `db/migrations/postgres/`: today's eight files, unchanged.
- `db/migrations/oracle/`: `001_baseline.sql` equal to the Postgres schema as of 008 (no data migrations), then one
  file per later change. Every later schema change ships in both folders in the same pull request.

Oracle DDL commits implicitly, so a failed migration can leave a half-applied file. Rules for the Oracle folder: one
DDL statement per step, steps separated by a `-- step` marker, each step recorded in `schema_migrations` as it
succeeds, and every step safe to re-run where possible. PL/SQL blocks (triggers) use `/` terminators and the runner
splits on them. A CI check compares the two schemas (tables, columns, constraints, indexes by name) after migrating
both, so a change made in one folder only fails the build.

A generator from one source (or Liquibase, which several banks already run) is the alternative. It is more work up
front and still needs hand edits for partial indexes and triggers. Reconsider if a bank asks for Liquibase changelogs.

### 4.6 Tests against both databases

- `test/helpers.ts` gets a `resetDb()` per dialect. Postgres keeps `drop schema`. Oracle drops all tables owned by the
  test user (or recreates the user) and runs the baseline. Recreating the user is slower; truncating every table and
  restarting identities between harnesses is faster once the schema exists.
- Raw SQL in tests (76 calls) moves to a small test helper (`count(table)`, `statuses(...)`, `setCreatedAt(...)`) so
  test bodies stay dialect-free. `v11-general-review.test.ts:177` inserts an order with `'{}'::jsonb` and `interval`
  and needs a rewrite.
- CI: a matrix job with `postgres:16` and `gvenzl/oracle-free` (23ai Free, `APP_USER`/`APP_USER_PASSWORD` set). The
  image takes about a minute to become healthy; use its `-slim` variant and a health check. 23ai Free accepts 19c
  syntax, but it also accepts 23ai-only syntax (`BOOLEAN`, no `FROM dual`, `GROUP BY` positions). Enforce 19c in
  review and with a lint on `db/migrations/oracle`, and run against a real 19c database (an image built from Oracle's
  container scripts, or a bank test environment) before each delivery if the banks run 19c.

### 4.7 Empty string is NULL

Oracle stores `''` as `NULL`. A `NOT NULL` text column given `''` fails with `ORA-01400`; a nullable one silently
turns `''` into `null`, and `where col = ''` matches nothing. Proposed:

- Zod schemas reject empty strings for every value that lands in a `NOT NULL` text column (`.min(1)`).
- Repositories normalise `''` to `null` on write for nullable columns, on both databases, so behaviour is identical.
- Add `CHECK (col <> '')` style constraints on Postgres for the same columns, so Postgres fails the same way Oracle
  does and the bug shows up in today's CI.

### 4.8 Booleans

19c has no SQL `BOOLEAN`. Use `NUMBER(1)` with `CHECK (col IN (0, 1))` for `active` and `done`, write `1`/`0`, and
map back to `boolean` in the row mapper. Computed booleans (`exists(...) as used`, `pg_try_advisory_lock ... as ok`)
become `CASE WHEN ... THEN 1 ELSE 0 END`. When every bank is on 23ai, switch to `BOOLEAN` with one migration.

### 4.9 JSON storage

On 19c, `CLOB CHECK (col IS JSON)` for all seven JSON columns. Writes bind the serialised string (already produced
with the `bigint` replacer in event-store.ts and events.ts). Reads parse the string in the mapper. The only JSON path
query (reports.ts:51) becomes `JSON_VALUE`. Large configuration documents (`config.data`) are fine in a `CLOB`. On
21c+, the native `JSON` type is faster and node-oracledb returns objects directly; the mapper handles both.

### 4.10 Identifiers and reserved words

Oracle 12.2+ allows 128-byte identifiers, and every table, column and index name here is under 30 characters anyway.
Unquoted names fold to upper case in Oracle; result rows will come back as `PAIR`, `BOOK_PRICE`. The Oracle `Db` sets
`outFormat` to objects and lower-cases keys once, so mappers see the same names. Avoid reserved words as aliases
(`start` in routes/customer.ts:134).

## 6. Open questions for the team

1. Which Oracle versions do the target banks run in production? 19c only, or 21c/23ai too? This decides JSON,
   `BOOLEAN` and how much 19c-specific code we keep.
2. Will a bank accept a Postgres database for this product at all, perhaps as an appliance we operate in their private
   cloud? If every bank says yes, Oracle support may not be worth 18-27 developer-weeks now.
3. Do the banks allow a second instance-to-instance channel (Redis, or Oracle AQ with the grants it needs), or must
   the stream bus run over plain tables?
4. Will bank DBAs grant `EXECUTE` on `DBMS_LOCK`? The plan does not need it, but it would allow keeping session-held
   locks.
5. Does the bank expect a reporting feed into its data warehouse (fills, settlements, fees, positions)? If so, in
   which form: views in our schema, a nightly extract, GoldenGate or CDC on our tables? This affects naming and which
   columns must stay stable.
6. Who owns schema changes in production at a bank: our migration runner on startup, or the bank's change process
   (scripts reviewed and run by a DBA, perhaps Liquibase)? The Oracle folder must support running outside the app.
7. Character set and string limits: is `AL32UTF8` and `MAX_STRING_SIZE=STANDARD` the norm? This decides `VARCHAR2`
   lengths for Turkish text in `reason`, `display_name` and `last_error`.
